## 语言约定

- 与 Claude 沟通、代码注释、TODO、计划文档：中文
- 代码标识符（变量/函数/类/包名）、文件名、目录名、Git 分支名：英文，禁止中文路径

## 依赖与安装规范

**分级规则：**
- 项目级（默认）：项目代码用到的库，一律装进项目环境——Python 用 `uv add <包>`，Node 用 `npm install <包>`；禁止用 `pip install`、禁止 `npm install -g` 安装项目库
- 用户级（例外，满足其一即可）：① 多个项目共用且版本不敏感；② 社区公认用户级安装的工具（uv、node、fnm、git 等）

**用户级安装三步流程（必须完整执行）：**
1. 安装前：醒目向用户声明——装什么、为什么用户级、安装到哪，确认后执行
2. 留存凭证：安装包默认保存到 `D:\BaiduSyncdisk\software`；**只在真正保存安装包时询问用户是否使用此默认路径**。若无独立安装包（如脚本安装），导出安装引导（来源 URL、命令、版本号）存档到同一位置
3. 安装后：醒目总结——所装版本、安装位置、安装包/引导的存档处

**日常命令：**
- Python：`uv add <包>` 加依赖、`uv run <脚本>` 运行；`.venv/` 不提交不手改；`uv.lock` 必须提交
- Node：`npm install <包>` 加依赖；`node_modules/` 不提交；`package-lock.json` 必须提交

## 目录结构（新文件落位法则）

**第零问（优先）：项目所用框架/语言有惯例目录结构吗？**（如 Next.js 的 `app/`、Go 的 `cmd/`+`internal/`、Python src-layout、Java Maven 布局）有 → 跟随惯例；没有 → 走下方问法兜底。

```
├── src/          # 手写源代码
├── tests/        # 自动化测试（JS 生态盛行就近放置 foo.test.ts，此时跟随生态惯例）
├── docs/         # 设计文档、教程；docs/plans/ 放功能计划
├── scripts/      # 构建/部署/运维等自动化脚本
├── examples/     # 示例代码（库的使用演示）
├── assets/       # 图片、字体等静态资源（框架有约定目录时跟随框架）
├── tmp/          # 临时文件，随时可删（已 gitignore）
├── dist/         # 构建产物（已 gitignore，可重新生成）
└── 根目录        # 只放配置文件与 README / TODO / CHANGELOG 等全局文档
```

新文件落位前依次问：手写产品代码？→ `src/`；验证代码？→ `tests/`；自动化/运维脚本？→ `scripts/`；示例代码？→ `examples/`；静态资源？→ `assets/`；说明文档？→ `docs/`；过程产物或临时文件？→ `tmp/` 或 `dist/`。

两条原则：

- 禁止把文件散落在根目录
- 目录按需生长：出现上述问法都答不上的真实需求时才新建目录，并登记到「项目产物说明」；不预建空目录

## Git 工作流

- 分支：每个功能/修复开独立分支，命名 `feat/<功能>`、`fix/<问题>`（英文小写中划线）；完成后合并回 main 并删除该分支
- 提交：小步提交，每个提交只做一件事；提交前先格式化；格式见「语言约定」
- 禁止提交：`.env`、`node_modules/`、`.venv/`、`tmp/`、`dist/`（.gitignore 已拦截，不得绕过）

## 测试

- 关键功能（核心计算、数据处理、关键函数）必须配自动化测试，放 `tests/`
- 改动核心逻辑后运行测试（`uv run pytest` / `npm test`）并如实报告结果；界面类改动可手动验证

## 代码格式化

- Node 项目用 Prettier，Python 项目用 Ruff——作为**项目开发依赖**安装（`npm i -D prettier` / `uv add --dev ruff`），不装全局
- 每次提交前对改动文件执行格式化

## 敏感信息

- API 密钥、密码等只放 `.env`（已 gitignore），代码通过环境变量读取；禁止写进代码、文档或提交记录
- `.env.example` 与 `.env` 字段保持同步（只留键名和用途注释，不留真实值）

## 任务与版本

- `TODO.md`：三栏清单（待办 / 进行中 / 已完成）——开工前先读，完工后更新
- 大功能动手前：计划写到 `docs/plans/<功能名>.md`
- 功能完成后：`CHANGELOG.md` 记一笔；版本号从 0.1.0 起——修 bug 最后一位 +1，新功能中间位 +1，破坏性大改第一位 +1

## 交付与部署

任何交付或部署操作前**必须向用户确认**：

1. **交付/部署目标**：环境（开发/测试/生产/发布渠道）、版本、预期影响范围
2. **执行步骤**：具体要运行哪些命令、上传哪些文件、修改哪些配置
3. **回滚/验证方案**：出问题如何恢复、部署后如何验证成功

用户确认后再执行；执行后如实报告结果。禁止在未确认的情况下直接部署到生产环境或对外发布。

- 标注【一次性】的章节：执行完成后立即删除，并把结果写入「项目产物说明」，供后续开发识别使用
- 其余章节为常驻规范，默认保留；开发中若发现规范与现实矛盾，停下提示用户裁决，不得静默违背或擅自修改
- 本文件是模板：复制进项目后即为该项目自有规范文件，后续改动改项目副本、不同步回模板；确有通用价值的新规范，通过 `cc-agent-setup` skill 子功能的「可复用」路径写回模板库

## 【一次性】新项目初始化指令

> 本章节通常由 `cc-agent-setup` skill（`/cc-agent-setup` 触发）逐步执行；手动使用时由 Agent 按用户指令执行。全部完成后删除本章节，并填写「项目产物说明」。

1. 询问用户：项目名称、一句话目标、技术栈 → 填入「项目简介」
2. `git init -b main`
3. 生成 `.gitignore`：以**最小必需集**开始，按技术栈/运行环境追加，禁止一上来就复制大全。初始内容如下：

```
# 依赖与环境
node_modules/
.venv/
# 产物与临时文件
tmp/
dist/
# 敏感信息
.env
# 日志与系统文件
*.log
.DS_Store
```

追加规则（仅在确定对应技术栈/环境时使用）：
- Python 生态：`__pycache__/`、`build/`、`.cache/`、`*.egg-info/`
- Windows 开发机：`Thumbs.db`、`desktop.ini`
- 其他按项目实际出现的临时文件追加

4. 生成 `README.md`（双语：项目名与简介、安装步骤、运行方法；先中文后英文）
5. 生成 `TODO.md`（三栏：待办 / 进行中 / 已完成）
6. 生成 `CHANGELOG.md`（标题 `# Changelog`，首条 `## [0.1.0] - 未发布`）
7. 若项目确实需要密钥/环境变量，生成 `.env.example`（空模板，逐键注释用途，不留真实值）；否则跳过，待出现真实需求后再建
8. 目录按需创建、不预建空目录：`src/`、`tests/`、`docs/plans/` 在出现真实落位需求时再建，并登记到「项目产物说明」；若当前已有明确的首个模块/测试/计划，可即时创建并放一个 `.gitkeep`（`tmp/`、`dist/` 已被 gitignore，需要时再建）
9. 按技术栈初始化：Node → `npm init -y` 且 `npm i -D prettier`；Python → `uv init` 且 `uv add --dev ruff pytest`（uv 未安装时先按「用户级安装三步流程」安装）
10. 首次提交：`chore: init project (初始化项目)`
11. 删除本章节，填写「项目产物说明」：列出已生成的全部文件与目录及各自用途
12. 执行初始化检查清单：确认项目名称/目标/技术栈已填、所有 `<!-- TODO: -->` 占位符已处理、本章节已删除、项目产物说明已填写
