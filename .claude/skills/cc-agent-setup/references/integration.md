# 已有 CLAUDE.md 的整合策略

> 何时读本文件：目标目录已存在 CLAUDE.md，用户要求「引入规范 / 整合 / 对齐」。目标：补齐并对齐本体系的固定骨架，同时**用户自己的内容一个字不碰**。全程中文沟通。

## 铁三角原则

1. **用户内容不动**：维度规范章节与用户自加章节原样保留
2. **只对齐固定骨架**：补充或修复的仅限机制章节（模板使用说明、项目简介、章节维护、流程归属（可选）、【一次性】初始化、项目产物说明）
3. **确认后才写盘**：所有动作先出报告，用户逐项拍板后才执行

## 第零步：特例分流

先粗判已有 CLAUDE.md 是否属于本体系。识别特征：含「【一次性】」「项目产物说明」「章节维护」任一机制章节，或整体呈「模板使用说明 + 项目简介 + 维度规范章节」骨架。

**完全不是本体系文件**（如内置 /init 生成的代码库文档式 CLAUDE.md——以「描述现有代码库的结构/命令/规范」为目的）→ 不强行骨架化：

1. 向用户说明两者差异，建议改走子功能（references/claude-md-guide.md 五步工作流）生成新规范文件
2. 旧文件中有价值的信息（构建命令、目录说明、既有约定）作为子功能第一步的调研素材并入
3. 旧文件改名 `CLAUDE.old.md` 保留，由用户处置；不得删除

属于本体系（含部分机制章节）→ 走下面三趟算法。

## 第一趟：解析

1. 按 Markdown 标题树把已有 CLAUDE.md 拆成章节清单（含文件头部的引言块）
2. 逐章归类：
   - **固定骨架章节**：机制件（模板使用说明引言块、项目简介、章节维护、流程归属（可选）、【一次性】初始化指令、项目产物说明）
   - **维度规范章节**：语言约定、依赖、目录结构、测试等按十维展开的领域规范
   - **未知章节**：用户自加（如「部署笔记」「合作约定」）
3. 推断项目状态：项目产物说明已填写且【一次性】已删 → 已初始化项目；【一次性】仍在 → 初始化残留未收尾

## 第二趟：对齐

对照固定骨架逐项判定动作：

| 发现 | 动作 | 处理 |
|---|---|---|
| 骨架章节缺失（如无「章节维护」） | **补充** | 附默认原文，建议直接写入 |
| 骨架章节存在但被改动 | **对齐** | 列出差异；默认建议恢复固定原文，用户可保留其改法 |
| 【一次性】章节残留（已执行未删） | **清理** | 把其已执行的成果整理进「项目产物说明」后删除该章节 |
| 维度规范章节 / 未知章节 | **保留** | 一字不改；仅检查其内部交叉引用是否指向已不存在的章节，有则报告 |
| 用户内容与骨架机制冲突（如自定了另一套章节生命周期） | **裁决** | 单列请用户裁决，不擅自取舍 |

## 第三趟：合并与确认

1. 输出四栏整合报告：

| 章节 | 动作 | 理由 | 用户决定 |
|---|---|---|---|
| （逐项列出） | 补充/对齐/清理/保留/裁决 | 一句话说明 | 待定 |

2. 以 AskUserQuestion（每轮 ≤4 题）或对话逐项确认；「保留」项默认跳过不问，仅在报告中列出告知
3. **全部确认后才执行写入**；写入用 Edit 做精准改动，不整文件重写
4. 写入后输出最终章节结构清单，并提醒用户：后续规范演进按「章节维护」节执行（矛盾即停，请用户裁决）
